# Правило-роутер системных коммуникаций (спецификация)

_Назначение: по входным признакам события однозначно определять КАК его показать (канал, блокирующесть, приоритет, статус, частота). По этому правилу ревьюятся все новые сообщения._

> ⚠️ **Статус: PROPOSED.** Лестница приоритетов и правила очереди реконструированы из логики продукта — разработка их не подтверждала. Помеченные 🔶 пункты нужно валидировать после ответов дева (вопросы 5, 8 из чек-листа).

---

## 1. Входные оси (что мы спрашиваем о событии)

| Ось | Значения | Откуда берётся |
|---|---|---|
| **A. Класс события** | регуляторика · состояние аккаунта · бизнес-порог · real-time event · результат действия · онбординг/промо · техстатус | смысл события |
| **B. Критичность** | `blocking` (нельзя продолжить) · `action-required` (нужно решение, но не сейчас) · `informational` (к сведению) | продукт/легал |
| **C. Регион** | SIGAP_BRAZIL · NONE_MEXICO · BCE · all | воркгруппа |
| **D. Контекст экрана** | игровой (game/sport/esport) · обычный | текущий роут |
| **E. Повторяемость** | once-ever · once-per-session · every-time | бизнес-правило |

---

## 2. Шаг 1 — выбор канала (A + B → канал)

| Класс события (A) | `blocking` | `action-required` | `informational` |
|---|---|---|---|
| Регуляторика / легал | **Жёсткая модалка** (без закрытия) | Модалка с крестиком | Inline-баннер |
| Состояние аккаунта | **Модалка-форма** (блок) | Модалка-форма | — |
| Бизнес-порог / лимит | **Модалка** | Модалка | **Тост** |
| Real-time event | — | Event-модалка | Event-модалка / тост |
| Результат действия | — | — | **Тост** (success/error/info) |
| Онбординг / промо | Модалка-форма (если обязат.) | Модалка | Тост / баннер |
| Техстатус приложения | **Алерт** (форс-обновление) | Алерт | Тост |

**Базовое правило:** `blocking` ⇒ модалка без свободного закрытия; `action-required` ⇒ модалка/bottom-sheet с закрытием; `informational` ⇒ тост или inline-баннер (никогда не модалка).

---

## 3. Шаг 2 — приоритет и очередь (когда претендентов несколько)

Показывается **один** претендент с наивысшим приоритетом; остальные — по правилу справа.

| Приоритет | Что сюда входит | Если конфликт |
|---|---|---|
| **P0 — Жёсткий блок** 🔶 | SigapBlockModal, UpdateUserPassword, noDemoMode | Перебивает всё, в очередь не уходит, не откладывается |
| **P1 — Обязательная регуляторика/RG** 🔶 | AgeControl, LimitsAfterReg, SessionControl, KYC/ReKYC (форс) | Показывается после P0; остальные ждут в очереди |
| **P2 — Согласия / верификация** 🔶 | CookiePolitic, VerificationControl/SimpleReg | После P1 |
| **P3 — Онбординг / промо-модалки** 🔶 | FirstBonus, CouponsAfterReg | **Очередь, по одному**; не более 1 за сессию подряд |
| **P4 — Геймификация / выигрыши (event)** 🔶 | levelUp, vipStatusUp, wagerWin, referralWin, availableBonus, newCard, promoCodeInfo | Очередь FIFO; на игровом экране — **откладывать до смены роута** (см. §5) |
| **Тосты (вне лестницы)** | все T-/B- сообщения | Неблокирующий слой, показываются **параллельно** модалкам, стек/replace по своим правилам |

**Правила разрешения конфликта:**
- `suppress` — претендент ниже P-level отбрасывается, если активен P0.
- `queue` — претенденты P1–P4 встают в очередь и показываются последовательно.
- `defer` — P4 на игровом экране откладывается до выхода с игры.

> 🔴 **Главный незакрытый риск:** после регистрации одновременно претендуют P1 (LimitsAfterReg) + P3 (FirstBonus, Coupons) + P4 (event). Без подтверждённого правила очереди это «стопка» модалок. Правило выше — предлагаемое; нужно подтверждение дева.

## 4. Шаг 3 — региональный гейт (C)

Регион применяется **до** показа: один смысл может иметь разные компоненты по юрисдикции.

- KYC: `NONE_MEXICO` → KycModalControl · `SIGAP_BRAZIL` → ReKycModalControl
- AgeControl / SIGAP / Limits / Session → только `SIGAP_BRAZIL`
- Cookie → `BCE`
- FirstBonus → **НЕ** `SIGAP_BRAZIL`

**Правило ревью:** у каждого сообщения регион — обязательное поле. `all` допустим только если подтверждён для всех активных юрисдикций.

---

## 5. Шаг 4 — контекст экрана (D)

- На игровом экране (`game/sport/esport`) **неблокирующие** P4-попапы откладываются до смены роута (как vipStatusUp).
- **Блокирующие** P0 (например SigapBlockModal) показываются именно на игровом экране — это их триггер.
- UpdateUserPassword, наоборот, ждёт пока нет активных игровых экранов.

---

## 6. Шаг 5 — частота (E)

| Повторяемость | Механизм | Примеры |
|---|---|---|
| once-ever | persistent-флаг / cookie на аккаунт | Cookie-согласие, FirstBonus |
| once-per-session | session cookie | KycModalControl (`kycModalShowed`) |
| until-resolved | флаг состояния | UpdatePassword (до submit), ReKYC (до kycValid=true) |
| every-time | без подавления | тосты-результаты действий |

**Правило ревью:** у каждого сообщения должна быть указана повторяемость и механизм её хранения. 🔶 Сейчас для большинства не задана — запросить у дева.

## 7. Шаг 6 — статус → цвет/иконка (нормализация семантики)

| severity | Цвет/иконка | Когда |
|---|---|---|
| success | зелёный ✓ | действие выполнено (депозит ок, избранное добавлено) |
| info | нейтральный/синий | факт без оценки (вейджер не учтён, удалено из избранного) |
| warning | оранжевый | требует внимания, не ошибка (гео, лимит близко) |
| error | красный ✕ | ошибка/отказ (ошибка депозита, бонус не активирован) |

> 🔴 Сейчас нарушено: success помечен warning-оранжевым (T-04), негатив — зелёным success (B-01, B-05). Привести по таблице.

## 8. Как применять при ревью нового сообщения (чек-лист)

1. Определи **класс события** (A) и **критичность** (B) → канал по §2.
2. Проверь, что критичность не завышена (informational не должно быть модалкой).
3. Назначь **приоритет** P0–P4 (§3) → проверь, не конфликтует ли с уже существующими в этой точке флоу.
4. Укажи **регион** (§4) — `all` только если подтверждён.
5. Проверь поведение на **игровом экране** (§5).
6. Задай **повторяемость** и механизм (§6).
7. Назначь **severity → цвет** по §7.
8. Текст — через **i18n-ключ** по конвенции (не хардкод), с переводом на все локали региона.

Если все 8 пунктов заполнены — сообщение готово к разработке и встаёт строкой в матрицу.
