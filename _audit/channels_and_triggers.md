## B. Систематизация: какой канал при каком событии срабатывает

Срабатывание определяется **классом триггера**, а не экраном. Классов — 7, плюс сквозной гейт по региону.

| Класс триггера | Что инициирует | Какой канал | Блок? | Правило дедупликации |
|---|---|---|---|---|
| **1. Регуляторно-юридический гейт** | Возраст, SIGAP-блок, гео, cookie-согласие | Жёсткая модалка / inline-баннер | Да/частично | cookie «показано», флаг согласия |
| **2. Состояние аккаунта** | UNVERIFIED, passwordInvalidate, kycValid, ACTIVE | Модалка-форма (блок/полу-блок) | Да | закрывается при снятии флага |
| **3. Бизнес-порог / лимит** | Платёжный лимит, лимит проигрышей/ставок, таймаут сессии | Модалка (критично) **или** тост (информирование) | Зависит | по достижению порога |
| **4. Real-time event (socket notify)** | level / vipStatusUpdate / win / referral / new card / promo | Event-модалка | Нет | на игровых страницах **откладывается до смены роута** |
| **5. Результат действия пользователя** | Депозит, избранное, активация бонуса/промокода, ставка | Тост (success/error/info) | Нет | разовый, по факту действия |
| **6. Онбординг / промо после рег** | Завершение регистрации, доступные бонусы | Модалка обычная | Нет | redux-флаг показа, cookie |
| **7. Технический статус** | Доступно обновление, блок пользователя, нет демо | Алерт / модалка | Зависит | по версии/статусу |
| **Сквозной: РЕГИОН** | SIGAP_BRAZIL / NONE_MEXICO / BCE | гейт над всеми классами | — | один смысл → разные компоненты по юрисдикции |

**Как это читать:** одно и то же бизнес-событие может идти разными каналами в зависимости от критичности. Пример — лимит RG: мягкое информирование → тост (T-11/T-12), требование действия → блокирующая модалка (M-06/M-12). Сейчас **выбор канала под класс события нигде не зафиксирован как правило** — это и есть то, что нужно стандартизировать.

## C. Чего НЕТ в материалах — что запросить

### C1. Каналы, которые в продукте почти наверняка есть, но не задокументированы
| Канал | Зачем нужен / где обычно | У кого запросить |
|---|---|---|
| **Push-уведомления** (web/mobile) | реактивация, статусы выплат, промо | Backend / CRM |
| **Email / SMS** | KYC, безопасность, транзакции, промо | CRM / Notifications |
| **In-app inbox / центр уведомлений** | на Figma есть колокольчик с бейджем «31» и карточка «Notes» — канал не описан | Frontend / Product |
| **Inline-валидация форм** (ошибка под полем) | депозит, регистрация, лимиты | Frontend |
| **Сетевые/серверные ошибки как класс** | 5xx, timeout, offline — единый паттерн | Frontend |
| **Empty states / заглушки** | пустая история, нет ставок, нет бонусов | Design |
| **Промо-баннеры в ленте** (не модалка) | на Figma «The prize fund $20 000», «Best slot games» | Design / Product |
| **Tooltip / coachmark / онбординг-подсказки** | первые сценарии | Design |
| **Badge / счётчики непрочитанного** | привязаны к inbox | Frontend |

### C2. Метаданные, без которых матрицу нельзя достроить (запрос разработке)
1. **Resolved-строки по всем ключам и локалям** (BR / MX / …) — сейчас видны только ключи, не тексты.
2. **Полный каталог socket-notify типов** — раздел 2 дока («event-driven») явно неполный; нужен весь список событий.
3. **Правила приоритета и очереди** показа модалок (особенно конфликт после регистрации: FirstBonus / Coupons / LimitsAfterReg + event-попапы).
4. **Правила частоты / анти-спама** (как часто, сколько раз за сессию, cooldown).
5. **Маппинг severity → цвет/иконка** для тостов (сейчас семантика сломана).
6. **Полный список bottom-sheet'ов** (в доке их нет, на Figma есть).
7. **Захардкоженные строки** — список того, что НЕ идёт через i18n (cookie, Coupons, все event-модалки).

## D. Готовый чек-лист запроса разработке (copy-paste)

> Просьба выгрузить/подтвердить:
> 1. Все ключи локализации с резолвом по локалям BR/MX (и любым другим активным).
> 2. Полный список типов socket-нотификаций (notify type → какой попап открывает).
> 3. Все тосты/снекбары на стороне фронта (текст/ключ, severity, триггер) — в доке их нет.
> 4. Все bottom-sheet'ы.
> 5. Логика приоритета/очереди при одновременном показе нескольких модалок.
> 6. Правила частоты показа (per session / cooldown / max shows) по каждому компоненту.
> 7. Используются ли push / email / SMS / in-app inbox, и кто их контент-владелец.
> 8. Список строк, захардкоженных в коде (вне i18n).
> 9. Маппинг статус→цвет/иконка для системных сообщений.
